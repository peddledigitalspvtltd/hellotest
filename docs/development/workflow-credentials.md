# Workflow credentials

Workflow HTTP and external MCP nodes store a project-scoped `connectionId`, not the credential. Integrations management owns the connection endpoint, allowed methods/tools and authentication. The built-in HelloTest MCP connection instead uses the verified signed-in principal and project. Connection management requires integration permissions and current access to the owner project; workflow use is subject to the workflow route permission and fresh connection resolution.

Saved tokens and additional header values are encrypted with AES-256-GCM before entering `app_settings`. The connection ID and header identity bind the encrypted values through authenticated additional data. `WORKFLOW_CREDENTIAL_KEY`, or the configured session secret fallback, must have at least 32 characters; all workers need the same configured key. Server environment references are limited to `AGENTIC_SECRET_*`. Public connection contracts use a field whitelist and masked header values. Encryption keys, ciphertext and credential values are never returned by those contracts.

Supported authentication is None, Bearer, Basic and a named API-key header, with optional encrypted additional headers. Basic's existing API contract accepts `username:password`; the captured username must agree with that runtime identity, including environment-backed credentials. OAuth authorization/refresh, digest, query/body credentials and dynamic secret expressions are not implemented and are not advertised. Endpoint query parameters remain usable for ordinary filters and cursors; credential query keys are rejected. Changing the server origin requires resupplying saved encrypted credentials and header values rather than silently moving them to another host.

Runtime credential resolution happens immediately before the pinned HTTP/MCP transport dispatch, after project and destination checks. DNS addresses are checked and pinned; private destinations require a managed connection, metadata endpoints are rejected, redirects are not followed, and body/response/deadline limits apply. API diagnostic tests use the same path, so a legacy inline credential or raw private-host diagnostic cannot bypass that policy. Writes retain their received/unknown outcome semantics without automatic replay.

Connection-aware response redaction removes complete secret values, encoded forms and Basic passwords echoed separately. Sensitive response fields include authorization, cookies, tokens, refresh tokens and client secrets. New workflow definitions reject retired inline credential objects and authentication expressions. Legacy workflow and run snapshot reads sanitize those retired fields before serving them or creating another snapshot, while retaining managed references and nonsecret metadata. This is targeted credential protection: arbitrary business content in input/output payloads is not interpreted as a credential store.

The reference patterns are n8n's separation of [saved credentials](https://docs.n8n.io/credentials/) from node data, [HTTP authentication types](https://docs.n8n.io/integrations/builtin/credentials/httprequest/), [HTTP node request configuration](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.httprequest/), and [shared encryption-key requirements](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/set-a-custom-encryption-key.md). These inform the boundary; they do not imply support for every n8n credential or node option.

Regression coverage includes encrypted persistence and masked CRUD, project isolation, origin changes, malformed values, matching Basic identity, separate password echoes, legacy definition/snapshot sanitization, and real local HTTP/MCP dispatch. The focused tests are `workflowConnectionSettings.test.js`, `workflowConnections.test.js`, `workflowCredentialPolicy.test.js`, `workflowHttpExecution.test.js` and the API diagnostic cases in `agentWorkspaceReliability.test.js`.
