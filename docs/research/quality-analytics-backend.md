# Quality Analytics and Release Readiness: backend evidence audit

Reference research: dated observations and verification counts describe the recorded review, not current acceptance. Use the current [verification runbook](../development/verification.md) for reproducible checks.


Reviewed and implemented on 10 September 2026. This document concerns the current dashboard data contracts, not an evaluation of release success prediction. The new Quality Analytics endpoint calculates observable inventory and execution outcomes; it does not calculate approval or model-confidence scores.

## Findings and implemented corrections

| Finding in the inherited implementation | Implemented behavior and source |
| --- | --- |
| Quality Analytics assembled several capped workspace collections, including a 100-case/story sample, and calculated project percentages from that sample. | [`GET /analytics/overview`](../../services/dashboard/backend/routes/qualityAnalytics.routes.js) now returns full current-project aggregate counts, a selected execution cohort, bounded attention items and ten recent runs. [`qualityOverview.service.js`](../../services/dashboard/backend/services/qualityOverview.service.js) uses five evidence queries regardless of record count; unavailable sources are not queried. |
| Retried cases and data rows had inconsistent deduplication across dashboards. | Execution totals select the newest attempt for each **run, test case and data row**, ordered by creation time with a stable ID tie-break. A newer pending/paused attempt replaces its older passed/failed attempt. Different runs and data rows remain distinct. The database performs this reduction before returning one aggregate row per run. |
| A completed observed row could hide other unexecuted rows in the frozen dataset. | Planned denominators include frozen case rows, falling back to the run dataset according to the execution resolver. Key/value data counts as one iteration; table `rows` or `template_rows` retain their declared length. Missing result rows remain pending. Recorded result rows outside a snapshot are retained rather than silently discarded. |
| Release readiness matched `release OR build`, omitted captured case scope and consumed its result budget with old retries. | [`executionResults.routes.js`](../../services/testing/backend/routes/executionResults.routes.js) now matches normalized release and sprint fields exactly, selects latest attempts before applying its result limit, and returns safe `{test_case_id, expected_iterations}` snapshots. Raw parameter, configuration, dataset values and bulky logs are not included. |
| `created_at` impersonated execution freshness, particularly after pause/resume. | Readiness results expose `updated_at` derived from valid lifecycle/timer/start/end timestamps. The overview also accounts for the latest lifecycle event. It distinguishes actual execution start from record creation and excludes future run cohorts and future-created attempts. |
| A dashboard or insight grant could bypass the permissions on records retrieved for explanations. | The overview checks project membership and `dashboard.view`, then checks Story, Case, Suite, Run/Result, Bug and automation grants and their feature policies independently. API-key scope checks use the same existing guard. Unavailable counts are `null`; their lists are empty and exclusions are disclosed. The legacy record-rich Explain endpoint now requires every returned manual source before reading it, and excludes automation coverage when its capability is unavailable. |
| The Explain UI expected `insights`, `release_summary` and `project`, while the service only returned differently named legacy fields, leaving its findings list empty. | The response now includes compatible canonical fields, real finding-specific evidence references, scope kind and project metadata while preserving legacy aliases. |
| Legacy Explain run counts were reconstructed from the globally latest result per case, so an older run lost its results when that case ran again. | [`qualityAnalytics.service.js`](../../services/dashboard/backend/services/qualityAnalytics.service.js) now uses a separate grouped per-run result query. Its summary reports scope and open evidence gaps instead of confidence percentages. Source links to deleted or foreign-project cases do not establish coverage; explicitly foreign-project Bugs cannot enter scope through incidental links. Future completions do not count in trailing throughput. |

## Contract and denominator choices

Inventory is the **current project**, independent of the 14-, 30- or 90-day execution window. Story coverage counts valid same-project case links, including the primary legacy Story link. Designed cases contain at least one saved test step. Automated inventory uses the case's explicit `automated = yes` designation; readiness or generated-code flags do not prove completed automation.

Execution totals cover latest run/case/data-row attempts for runs in the selected UTC cohort. Passed and failed form the assessed pass-rate denominator. Blocked work is displayed separately. Skipped/N/A, aborted and cancelled outcomes are combined in `other`; they are not silently treated as passes. Pending includes missing planned rows and nonterminal outcomes. Workflow completion, if shown, must identify that finalized skipped/aborted outcomes differ from successful validation.

The trend groups runs by end time, start time or creation time, in that order. Its daily points show the **current outcomes of runs assigned to each UTC day**. They are not a reconstructed history of the project's status on that date. Every day in the selected calendar window is returned, including zero days. Current source inventory and historical execution cohorts must not be represented as the same denominator.

A successful overview has loaded all permitted sources. It reports policy exclusions in `evidence.limitations`, rather than marking unavailable evidence as zero. A failed permitted source rejects the request; it does not publish a partial success. Release readiness remains explicitly bounded: `complete`, `reasons`, scanned counts and limit-plus-one candidate counts disclose truncation. Candidate counts are **lookahead counts, not exact full totals**. The API is documented in [`openapi.yaml`](../../openapi.yaml).

## Primary-source research and interpretation

- [PostgreSQL window functions](https://www.postgresql.org/docs/current/tutorial-window.html) explain that partition ordering controls `row_number` and tied values otherwise have unspecified ordering. This supports explicit run/case/row partitions and deterministic secondary ordering. It does not define which business attempts should supersede one another; that choice follows this product's persisted execution lifecycle.
- [Google SRE monitoring guidance](https://sre.google/workbook/monitoring/) distinguishes measurement sources and treats freshness as an operational property of monitoring data. This informed separate evidence timestamps, current inventory versus execution cohorts, and explicit incomplete/failed-source treatment. The implementation does not equate a recent timestamp with complete or correct test coverage.
- [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) recommends least privilege and checking permissions on every request. Applied here, permission to open analytics is separate from permission to disclose underlying Story, Case, Run or Bug evidence. Feature policy further restricts availability; it is not a replacement for authorization.

## Verification and remaining boundaries

Focused backend, authorization, readiness and OpenAPI tests passed (**51 checks**). [`qualityOverview.test.js`](../../services/platform/backend/test/qualityOverview.test.js) and [`releaseReadinessEvidence.test.js`](../../services/platform/backend/test/releaseReadinessEvidence.test.js) cover forbidden/disabled sources, failure propagation, invalid windows, UTC boundaries, source-safe payloads and bounded metadata.

[`qualityOverview.postgres.test.js`](../../services/platform/backend/test/integration/qualityOverview.postgres.test.js) passed against a **separate disposable PostgreSQL 16 container and empty `agent_verify_*` database**. It exercises actual SQL with 250 records, foreign/deleted and legacy primary links, reruns, stable ties, multiple data rows, missing rows, future timestamps, UTC boundary runs, exact release filtering, run-inherited data rows, restricted-source aggregates and the legacy Explain run-count query. No live workspace records were changed. The temporary container is removed after verification. The first full backend run exposed an inherited retry-test event-loop cancellation: its mocked transport has no socket, while the production retry timer is intentionally unreferenced. The affected test now keeps a bounded simulated connection alive with test-cleanup disposal; its retry/security assertions and production retry behavior are unchanged. The final full backend suite passed **609 tests, with one explicit skip and zero failures or cancellations**. The parent implementation report records final services/platform/frontend/build/browser results.

The existing custom-dashboard/legacy Explain compatibility fields still include advisory weighted scores. They have not been reclassified as measured probabilities; the new overview does not consume them, and Explain provenance identifies their heuristic nature. This work does not establish production-scale latency guarantees, historical time-travel analytics or measured prediction accuracy. The overview intentionally exposes aggregate task destinations rather than claiming its attention links open unsupported exact filters. Release readiness's bounded evidence is still a review boundary, even when the overview has full aggregate counts.
