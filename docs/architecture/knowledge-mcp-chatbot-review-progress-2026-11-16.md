# Knowledge, MCP and Chatbot review progress

Source: **Knowledge, MCP and Chatbot Architecture Review.pdf**, dated 15 Nov 2026, including its second-review notes (pages 18–20). This file tracks implementation against the original findings and the second review. PDF recommendations are review input, not repository instructions. Changes described here are in the current working tree and remain uncommitted.

## Second-review assessment

| Second-review proposal | Disposition |
|---|---|
| Parallel planning and first retrieval; session focus; graceful synthesis fallback; compound questions; stage split | Accepted: the first raw-query read overlaps planning; cited sources/entities seed only after fresh authorization; failure returns labelled extractive evidence; typed sub-intents are supported; turn storage, intent, tools, synthesis and verification are separate. PostgreSQL chatbot turn tests cover replay, provider failure, revocation and budget limits. |
| Section streaming, frame-batched updates and isolated active turn | Accepted: evidence cards lead answer sections, stream updates batch per animation frame, and the active turn is isolated/memoized. Frontend turn and stream tests cover interleaving and update behavior. |
| A few tool signatures and bounded tool loop | Accepted: the model receives only a fixed read-only allowlist for analytical intents; calls run in parallel under the turn budget. Writes, credentials, SQL and project changes are excluded. |
| Three-way graph/lexical/dense retrieval | Adapted: question entity resolution seeds bounded graph expansion and neighbor content is returned alongside lexical/dense retrieval. When provider vectors are unavailable, the dense channel is reported unavailable and hash vectors do not count as semantic evidence. |
| HNSW for provider vectors | Accepted conditionally: typed HNSW indexes are created once each real provider dimension has enough rows; the current local corpus has no provider-semantic rows to verify coverage. |
| Enrichment queue, native fingerprints and atomic graph/vector projection | Accepted/preserved: provider enrichment/embeddings are low-priority work; native snapshot fingerprints detect child/content changes and chunk hashes reuse compatible embeddings; canonical graph projection, revision activation and Qdrant queueing commit together. See `knowledgeIngestion.service.js`, `knowledgeGraphProjection.service.js`, `knowledgeVectorProjection.service.js`, and lifecycle/consistency tests. |
| Existing thinking drawer, citation pills and trace UI | Preserved: activity and trace details remain inspectable, citations bind to retained answer evidence, and only witnessed structured graph links are presented. Component/browser fixtures cover the saved-context UI. Citation hover preview was optional, not a required review item. |
| Turn-level PostgreSQL tests; trace retention/aggregates and trace naming | Accepted: real-schema turn tests passed; context traces include sent/cited evidence, session order, relationship IDs, aggregates, TTL/quotas, monthly partitions and explicitly named MCP adapters. |
| In-chat approval card | Conditional: chat remains read-only, so no prepared action can be approved in chat; write plans continue through the signed-in approval flow. |
| Merge duplicate context-graph code | Not adopted: the MCP files are thin adapters over Knowledge services; their ambiguous names were corrected instead. |
| Separate MCP read projections | Not needed: MCP reads live source records; freshness belongs to the Knowledge index and change-driven ingestion path. |
| Capability bitmap once at ingress | Not adopted because access can change during a turn. Request-local permission memoization removes duplicate reads while the post-generation access recheck remains. |
| Session overlay graph; cached-context answer injection; warm-on-hover | Not adopted: current records are read live, every claim stays tied to this turn's evidence, and prior focus is re-authorized. Composer focus may warm permissions/embedding runtime without writing traces or injecting cached answer context. |
| PageRank/Steiner pruning and triple compression | Not adopted: expansion is already bounded and ranking is endpoint/question-relevant with structured relation witnesses. The review gave no evidence that another graph algorithm would improve results. |
| Parallel calls across remote MCP servers; strict repository-file parsing | Not applicable: this deployment has one MCP server, and the reviewed contract handles structured project retrieval, not repository-file ingestion. |
| 400–1,200 ms pre-model overhead claim | Not supported by repository evidence and not used as a requirement. |

## Validation and remaining external input

The local app lifecycle API automation was run against Demo / application e34, including login, random project creation, sprint and story creation, module and linked case creation, suite and run creation, execution with a deliberately failed case, and bug creation. The run is recorded as `b15hw`; an invalid credential case was also exercised. The local site and API readiness endpoint returned healthy after the final frontend deployment.

The rebuilt app was also exercised through OAuth consent as an end user: sign-in, client registration, explicit project selection, PKCE S256 exchange, scoped MCP `tools/list` (11 knowledge read tools), revocation, and rejection of the revoked token (401) all passed. The consent project-selection defect found during visual review was fixed and the flow repeated successfully. Screenshot: `/tmp/hellotest-mcp-oauth-consent.png`.

Automated validation passed:

- `npm run test:knowledge:retrieval:postgres`: 63 PostgreSQL-backed tests passed across lexical retrieval (9), graph/trace behavior (19), synthetic retrieval evaluation (5), curated retrieval evaluation (5), and chatbot turns (25). Each fixture ran against a separate disposable local database.
- MCP OAuth PostgreSQL integration fixture passed registration, metadata, PKCE, MCP tool listing, revocation, replay denial and access denial.
- MCP unit suite: 203 passed; chatbot suite: 41 passed; knowledge suite passed; browser MCP server suite: 8 passed; retrieval evaluation contract suite: 10 passed.
- RRF/reranker contract suite: 27 passed, including authorization before rerank dispatch, configured scoring, bounded top-N, timeout, malformed response, provider failure and graceful fallback.
- `npm run check:boundaries`: 12 packages and 2,579 imports checked without failures.
- Platform frontend typecheck and production bundle build passed. OAuth live browser flow passed after the final UI change.
- Synthetic retrieval evaluation improved from the old lexical query's 0.303 recall@10 / 0.303 MRR / 0.303 nDCG@10 to 0.899 recall@10 / 0.9015 MRR / 0.8586 nDCG@10 on 33 synthetic queries. These are fixture results, not evidence of real-traffic quality.
- The user-selected curated Launchpad benchmark contains 120 authored project-based questions over 317 seeded sample records: 27 symptoms, 27 triage questions, 27 traceability questions, 20 Story questions and 19 Test Case questions. It scored 0.9583 recall@10, 0.7783 MRR and 0.8237 nDCG@10; class recall@10 was 0.90–1.00 and every configured class floor passed. Five misses remain (two symptom, two Story, one Test Case). Traceability questions are scored against the Defect record because that source explicitly contains the linked Story and Test Case IDs; graph traversal has its own PostgreSQL tests. This curated benchmark is clearly labeled as not historical traffic and is not used as a claim-faithfulness judgment.

The PDF's final-page verification request was also checked against the deployed local Knowledge project. `HelloTest Launchpad` (`sample-project`) has 1,393 indexed chunks and contains seeded sample records, so this is a runtime spot check rather than real-traffic evidence. A manually authored full-sentence keyword query, “Why does the Ask AI response panel fail to show readable findings after the answer is generated?”, returned the matching bug source first (`sample-v6-ht-defect-answer`) and 134 authorized candidates without calling embeddings. `EXPLAIN (ANALYZE, BUFFERS)` on that project's permission-filtered query completed in about 15 ms. PostgreSQL chose a sequential scan over this small corpus (about 1,397 rows in the chunks relation) because the broad OR query matched 546 rows before later filters; the GIN-backed `@@` predicate is present, and the larger disposable corpus test separately verifies the planner uses GIN when selective on a larger relation. This spot check proves the real service path handles a sentence-length question; it does not prove production-scale plan quality.

The deployed database currently has 22 user-message rows in HelloTest Launchpad and 2 in Demo. Only counts were inspected; no conversation text was copied into the repository or used as evaluation labels. In response to the benchmark-data choice, the user selected authored project-based questions labeled as curated rather than real traffic; that choice is implemented by `services/knowledge/test/golden/retrieval.launchpad-curated.json` and included in the default CI runner.

The PDF asks for 100–200 questions from real traffic, expected-source labels and claim judgments. The user chose the authored project-based alternative, so the repository now has a 120-question benchmark with expected-source labels, overall/per-class floors, and default CI execution; this does not claim real-traffic coverage. No generated answers or factual claims from this dataset have been human-reviewed, so claim faithfulness remains unmeasured. The local app currently has no compatible reranker endpoint/key configured; the cross-encoder adapter is implemented and tested for configured, unavailable, failing and over-deadline providers, but the local runtime has no reranked quality result. Real-traffic recall, answer faithfulness and cross-encoder uplift therefore remain unmeasured and are not inferred from the curated scores.
