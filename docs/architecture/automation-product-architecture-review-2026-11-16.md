### Recording and playback

Recording is more than a successful start/finish response: the recorded instruction must retain the interaction's runtime meaning. The real PostgreSQL recording suite passed 8 checks, including nested step persistence without modifying the linked manual source or shared definition. Existing command/studio acknowledgement guards were reviewed and retained; their browser fixtures were corrected to return the real started/count receipt shape rather than weakening production guards.

The additional recorder parity changes separate keyboard Tab from browser-tab lifecycle; replay action-caused navigation as an observed URL wait and collapse redirect observations; preserve absolute viewport/element scroll positions; deduplicate remote wheel and double-click observations; and retain frame metadata. Coordinate clicks remain explicit valid coordinates. The initial entry is seeded from the actual reused browser page, and missing targets are not fabricated from human labels or a generic body selector.

A replay preflight runs before target preparation/replacement. Unsupported multi-tab, framed and drag recordings are rejected explicitly while the existing plan remains intact; this change does not introduce popup/frame/drag replay support. Filename-only uploads require a configured file parameter. Exact remote input and keyboard activation identities preserve modifier chords and prevent duplicate Enter/Space-derived actions. The recording screen explains the single-page boundary and directs complex flows to Automation Engineer. The focused compiler/binding/finish/flush suite passed 34 tests, and 23 real Chromium recording/playback/control checks passed, including local and remote capture followed by playback in a fresh browser and exactly-once Enter/Space submissions. The PostgreSQL persistence suite also passed all 8 checks again after the changes.

The native finish path had a separate confirmed lifecycle gap: it saved steps/readiness without a durable import receipt, then awaited optional learning/activity work. A follow-up failure could report failure after a successful save, and a retry could reject the changed plan instead of recovering that save. Native finish now uses the existing receipt service to commit the native plan, complete mixed-runtime readiness assessment and receipt atomically. Repository preparation stays outside the transaction; no model/network work runs inside it. Optional learning/status/event failures return warnings after the save. Concurrent identical imports save once, retries return the receipt before reading the recorder or preparing a target again, and later user edits remain intact. Changed input selections still conflict explicitly. The receipt/response contains code-free step summaries; saved test steps remain the authoritative native source.

Native domain preflight also runs before creating a linked target, so unsupported actions or invalid coordinates do not create a partial target. The focused native finish/persistence/platform/readiness suite passed 32 checks, including seven new tests executing the production finish orchestration with the actual receipt, persistence, compiler and readiness implementations against transactional storage ports. These are distinct from physical-device execution and the generic real PostgreSQL receipt tests.

### Automation Engineer and source preservation

The browser architecture already discovers upstream native tool schemas, acts sequentially on observed targets, refreshes observations after transitions, preserves emitted operations once, saves completed sections progressively and stops on uncertain transport/mutation outcomes. These are reviewed existing protections, not newly introduced browser-agent features.

The new source fallback applies only after executable source is validated. Unsupported display mapping or a mapper/model dependency failure produces one custom instruction per prepared source operation, preserving source SHA-256, operation ID, kind and nesting depth. It does not regenerate or discard the source. Mapping/schema rejection receives its existing bounded correction attempt; dependency failure does not trigger a repeated failed display-model call. Critical cancellation, deadline and access failures still stop the build.

Every buffered completion phase now receives the remaining case time allowance. Guards run before and after provider work and asynchronous access/progress boundaries. A response arriving after cancellation or the deadline cannot authorize another browser action or become a saved section.

A genuine transport timeout after a browser mutation now reaches the sanitized terminal unknown-outcome receipt instead of escaping through the early fatal-error guard. Click/fill/press/navigation cannot be retried when their actual outcome is unknown. Cancellation, authentication, lease and read-deadline guards retain precedence.

### API source intake and ordered execution

The creation flow for API-capable and Unified applications contains a source-review panel. The user can paste source or select a file, inspect ordered methods, actions, request URLs, retained assertions/captures and review notes, then add after existing steps or explicitly replace the draft. Add is the default when a draft already contains steps. Invalid source has no Apply action; parameter conflicts retain the source and preview for correction. Applying a source parses locally and sends no target request.

The resulting draft saves one case with one canonical `api_request` per ordered step. Source defaults and private parameter metadata survive creation; an imported contract does not have to be regenerated by an LLM. The ordinary collection importer deliberately retains its existing **one case per request** grouping while using the same canonical parser.

| Source | Supported behavior | Review boundary |
|---|---|---|
| Postman | Nested folders, inherited authentication/defaults, scoped aliases for conflicting folder variables, raw/form request bodies, source-backed statuses, direct static response checks and JSON-variable captures. | Scripts are parsed as data and never executed. Conditional, mutating or unsupported scripts remain review notes; conflicting statuses are not promoted into unconditional assertions. |
| Multiple cURL commands | Ordered methods, URLs, headers, supported body/query/cookie flags and private authorization bindings. | No shell execution, substitutions, pipes, redirections or local file reads. Unsupported options/file bodies fail the whole import. cURL supplies no response status assertion by itself. |
| HAR | Recorded request order, supported bodies/headers and observed response statuses. | Captured response payloads are not copied. Volatile IDs, authentication and business expectations require review. Recorded status is an observation, not evidence of a new successful execution. |
| OpenAPI/Swagger JSON or YAML | All declared supported operations, local references, explicit request examples/defaults, path/query/header values, documented response outcomes and correct API-key security locations. | Missing bodies/values become explicit blank Test parameters; schema values are not invented. Multiple servers/examples/media types/security alternatives produce review notes for the chosen representation. Document order is not a verified business journey. |

The canonical result contains `steps`, `parameter_values`, `private_parameter_names` and `warnings`. For example, a login response can capture `t.token`; the next step can use `Authorization: Bearer @t.token`. Imported credential literals are removed into blank private inputs, including opaque variable names identified by their authorization/query/password context. Canonical review/apply data excludes the credential values. The source textarea remains a local editable copy of what the user supplied until cleared/applied.

Bounds are 2 MiB source/expanded draft, 200 requests, depth 40 and bounded traversal. YAML aliases are disabled and duplicate keys rejected. External references/examples, multipart/binary/file bodies and unsupported semantics reject atomically rather than returning a successful prefix. Unstructured prose documentation must use the existing agent brief or be supplied as OpenAPI/explicit cURL; the deterministic importer does not manufacture requests from prose. Unknown outcomes remain without an assertion, rather than silently becoming HTTP 200.

### Worker execution, evidence and compression

API workers use the complete decoded response for assertions/captures, bounded by `TESTENGINE_API_RESPONSE_MAX_BYTES` (8 MiB default, 32 MiB maximum). Reading remains subject to the original cancellation/deadline. An oversized body fails explicitly, retains HTTP status/headers and produces no captures from a partial prefix. A separately bounded 64 KiB UTF-8 diagnostic includes truncation and size metadata; a truncated prefix is not represented as complete parsed JSON. Compose/Kubernetes environment contracts carry the limit.

Manual API preview retains its separate 2 MiB bound and now cannot pass body assertions or capture values from a clipped prefix. Both API paths redact private inputs/captures before generating base64 SVG diagnostics and distinguish a missing header from an empty-but-present header. Raw capture values remain available inside runtime state for the next request.

Native clients validate ordered receipts rather than accepting reordered or incomplete successful subsets. A failed/blocked result can end an ordered execution prefix; success requires every requested step. Native screenshot evidence is limited to 8 MiB per block and reports unavailable/over-budget captures without rewriting completed device results. Android/iOS capability lists advertise implemented captures consistently.

Optional owned browser-video compression already preserves the original artifact and falls back safely on failure. The Dockerfile now explicitly installs/verifies ffmpeg with VP9 encoder support. A real WebM compression smoke passed; this change is a dependency/encoder guarantee, not a claim that the previously deployed image lacked ffmpeg. Native PNG screenshots are compressed images already. Native device video and per-line traces remain unimplemented.

## Execution limits and remaining validation

- No live funded LLM completion or complete model-driven browser-agent journey is claimed. Provider fixture tests validate contracts and failure handling, not current provider credits/availability or model quality.
- The in-app Browser connection was unavailable during this review. Chromium/Vite fixture verification is real browser execution, but is distinct from signing into `localhost:8080` and performing the whole task as an end user.

- Existing command/studio acknowledgement logic, Sprint v4 nodes, deterministic mapping, pairing architecture and evidence compression were retained where review/tests supported them. Their presence is not attributed to this change set.
