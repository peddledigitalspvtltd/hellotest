# AI Controls

Administration → **AI Controls** replaces workspace Settings → Prompt key mapping. Quality metric formulas and criteria are managed separately in Administration → Metric governance; they are deterministic business rules, not generation controls.

The shared catalog in `services/platform/shared/aiFeatureCatalog.json` defines stable feature identities, families, operation aliases, initial configurations and detailed instruction blocks. It covers Story authoring/grooming/assurance, Test Case design, automation, execution, Defects, test data, knowledge, content, built-in specialists, browser planning/decisions, and administration prompt optimization. `services/platform/shared/aiPromptDefaults.json` is a public projection for the existing frontend prompt hook; its consistency is checked in tests.

## Configuration and publication

Each feature has role, task, domain, primary prompt, categorized request templates, guardrails, sampling, provider preference, output cap, optional JSON Schema constraints and MCP context policy. Schema constraints supplement the native artifact shape. HTML authoring does not accept a JSON object schema. Permission checks, typed artifact validators, tool contracts, spending ceilings, source ACLs and approval of writes remain application rules.

Save draft stores a configuration without changing generation. Publish uses an expected revision, a transaction-scoped PostgreSQL advisory lock and an administrator audit entry. Competing edits receive HTTP 409. Reload latest makes reconciliation explicit. Publication history keeps 30 snapshots in separate setting records; routine generation reads only the published configuration and revision. Restore publishes a prior snapshot as a new version. Default/legacy prompt and provider preferences remain effective until a feature is published.

The workspace preference endpoint rejects writes to the retired prompt/provider mapping keys. Workspace metric criteria and formulas retain their existing permission controls. Server-side provider selection uses published preferences through the shared settings service. Explicit user selections take precedence; integrations tied to another project are rejected, including a global fallback that would cross project scope. Individual built-in specialists have their own provider and generation configuration; successor calls receive the successor's profile. Knowledge-stage preferences resolve before provider-specific cost reservation. Embedding entries expose metrics; their model is managed on the Knowledge Assistant integration so document/query dimensions and egress remain compatible.

## Model request boundary

`aiFeatureRuntime` resolves the effective published configuration before MCP retrieval and request-policy preparation. Detailed instruction markers expand before dispatch, input budgeting and trace capture, including reduced-context compatibility requests. Dynamic inputs, images, exact allowed IDs, current enum values and native domain validations are preserved. Marker references without a feature mapping fail explicitly rather than reaching the provider.

Sampling and output caps come from configuration. Smaller operation/request spending bounds still apply. Reasoning-model sampling restrictions and explicit provider compatibility negotiations remain effective. Additional object schemas are compiled before publication and validated locally against responses; no remote references, executable schema expressions or regex validation are accepted. A schema failure is reported without automatically replaying a paid generation.

Additional automatic project retrieval uses the built-in MCP gateway with the verified current user/project. Administrators can select task input only, evidence budgets, focus and whether successful retrieval is required. Selected drafts and user-provided inputs remain task data; changing context policy does not erase these inputs. Optional retrieval failures produce an explicit evidence-gap notice. Required retrieval failures stop generation and are traced. Context planning, ingestion and embeddings cannot recursively request MCP context. Existing knowledge pipelines handle their authorized MCP packets rather than retrieving the same packet again at synthesis.

## Optimization and observability

Optimize prompt sends only the feature definition being edited to the configured optimizer integration. It does not retrieve a project's private evidence or impersonate a project user. The model reviews all request templates and may propose role, task, domain, prompt, guardrail and existing template improvements. Only registered template keys can change. The portal shows the changed fields for review; using a suggestion edits the draft and never publishes it. The operation is audited and traced with an explicit instance scope.

Trace capture records stable feature/family, published configuration version and fingerprint, referenced instruction-profile versions, provider request/response, usage when reported, MCP status and corrections. Instance calls have a null project and a verified actor. Existing project trace APIs still require exact project scope. Admin metrics expose aggregate feature/operation counts, failed/invalid responses, corrections, MCP gaps, latency and tokens for the last 24 hours under the existing 14-day trace retention. Unknown usage and trace-write failures remain explicit. These are model transport/contract metrics, not semantic correctness or release-readiness scores. Cost is not invented when provider pricing is unknown.

## Context and guidance review

The shared request policy honors explicit user guidance within the feature task and native output schema. Story creation/completion, case authoring, synthetic test data and execution-planning blocks distinguish that guidance from untrusted retrieved documents. Provider size fallback preserves user guidance and bounded acceptance/specification excerpts; it retains a small MCP evidence packet with citation identities and explicit omitted-evidence limits. Tool conversations are never reduced by dropping tool calls or results.

Automatic MCP queries use task data before managed instruction blocks expand, so schema scaffolding cannot hide the selected artifact behind the retrieval query limit. Smart Context queries include acceptance arrays, executable specifications and Gherkin scenarios. Configured context/item budgets disclose omitted evidence. Required retrieval rejects an empty or over-budget evidence set. Budgets are conservative character estimates; exact provider token counts remain controlled by the common request-policy boundary.

Live Story evidence carries bounded planning/specification metadata. A separate supporting packet contains minimal related-Story metadata, permitted comment excerpts and attachment references. Comment and attachment permissions are checked before reads and again before synthesis; revoking supporting access leaves the base Story packet independently usable. Attachment metadata never claims the file contents were inspected. File content still comes from authorized indexed extraction or explicitly supplied compressed images.

The feature inventory contains 72 profiles. All static feature markers and model-generation operations map to the catalog; project-defined agents inherit the managed workflow profile while retaining their native contract. Provider connection probes remain diagnostics. Embedding controls remain bound to the Knowledge Assistant integration to preserve index compatibility. Outcome rows now separate published configuration versions and expose successful transport responses alongside failed/invalid responses; these do not measure factual accuracy.

Dedicated runtime selection now covers Story description rephrase, Story/Test Case change-impact review, failure clustering and Story Gherkin generation. Impact review supplies both saved and proposed snapshots while preserving native deterministic links and scores. Gherkin uses exact client identifiers and acceptance-criterion references, rejects cross-Story citations, duplicate mappings, missing Given/When/Then steps and generic placeholder templates, and explicitly requires semantic human review. Stories without criteria are excluded before the model call. Both full and provider-size fallback inputs preserve the user's guidance.

Three registered profiles (`ai.quality.gate_assessment`, `ai.execution.case_triage`, `ai.agentic.browser_decision`) have no dedicated model invocation. The browser profile is a retained legacy baseline for the five dedicated browser agents. They are visibly reserved and read-only; publication and optimization reject them. Existing deterministic gate/triage services remain the active implementations. These profiles are excluded from claims of active LLM coverage. Rich-text HTML profiles cannot accept a JSON object output schema. Metrics use the recorded profile identity before considering legacy operation aliases, preventing shared operations from mixing sibling-profile outcomes.

Automation review, gap mapping, automation step rephrase and network-to-API mapping now send an explicit, allowlisted task profile instead of embedding another feature's prompt in generic generation context. Queued jobs persist and revalidate that profile before dispatch. DOM naming/extraction selects its own profile and receives the server-resolved app/project scope. Clients cannot select administrative, agentic or arbitrary profiles through an automation build. Step rephrase preserves guidance up to its declared 18,000-character input limit and carries it through size fallback.

Small text Story attachments are also read through the existing attachment authorization service, with project/Story identity rechecked against the downloaded record. Up to three text attachments are read concurrently under individual 600 ms deadlines, a 16 KB stream budget and 600-character model excerpts. The packet preserves each attachment ID/checksum and explicitly marks shortened or unavailable excerpts. Binary or large files remain metadata-only and require authorized indexed extraction or supplied compressed images. Compressed object streams close their upstream storage stream when a bounded read ends. TestEngine HTTP uses its own bounded transport and is excluded from model governance and model-outcome capture.

## Guided configuration and request inspection

Explore explains each section and where the feature is used. Instructions contains the main behavior prompt; role, domain and task identity are available under a collapsed scope section. Guardrails is one editor for evidence handling, request priority and uncertainty. Output contract contains conditional format guidance and optional additional JSON Schema constraints. Model & limits contains provider settings and conditional recovery. MCP context configures retrieval independently of task behavior.

Case authoring uses three normal conditional settings: Gherkin authoring, structured steps and context-size recovery. Step rephrase uses its own schema and recovery guidance. Story-to-Test-Case generation also exposes image compatibility guidance and the selectable template library. Data headings and pieces of a JSON response are no longer separate case-authoring prompts. The application supplies those fields through typed request data and code-owned native schemas.

Case generation separates `generation_request.user_request`, `selected_template` and `reviewed_context`, using the context markers already produced by the authoring UI. The explicit user objective chooses functional, NFR, performance, reliability, security or accessibility coverage within feature scope. Templates supply defaults and reviewed content supplies evidence. Stock prompts no longer force core positive or happy-path cases ahead of NFR-only instructions. NFR drafts use supplied workloads and measurements; missing targets are limitations rather than invented values. MCP queries prioritize the explicit objective and Story intent rather than JSON schema scaffolding.

The admin-only request inspector uses the same prompt builders and message composer as live case generation. It displays configured instructions, sample records, the native output schema, active format/recovery guidance and configured model/evidence settings. Other profiles clearly expose a feature-policy preview that excludes call-specific inputs and contracts. Inspection makes no model calls, performs no MCP retrieval and does not publish or change workspace records. Its response is not cached. Edited schema constraints are included, and stale inspections are cleared when the draft or sample changes.

## Compatibility and publication

Instruction format version 3 merges the former request-policy text into Guardrails. Stock legacy prompts and template priorities migrate to objective-neutral defaults; administrator-authored changes are retained. Reviewed format edits move to their named conditional setting. Other edited case fragments remain in optional `legacy.reviewed` guidance; unchanged headings, schema fragments and duplicate default instructions are omitted. Historical snapshots remain untouched until an administrator publishes or restores a reviewed configuration. Effective fingerprints reflect the compatibility conversion.

Earlier line-fragment migrations still compose reviewed version-1 edits before conversion. Saving a version-3 configuration does not repeat the migration. Early inline history snapshots are archived before history is reduced to metadata, preserving rollback across a new publication. Internal migration dictionaries are excluded from the public feature inventory.

Native field names, allowed identifiers, supported step types, item limits and permission checks are application contracts. Editable prompt text cannot grant access or approve a write. Existing general feature templates remain configurable under collapsed advanced guidance when a feature requires staged or specialized instructions. They are not additional model calls.

Recovery has two purposes: bounded schema/citation repair after invalid output, and context-size correction after a typed provider size rejection. Context-size instructions are configured per case feature, expanded before dispatch and added only to the smaller retry. Full and reduced requests preserve the explicit user objective and application contract. Network failures, throttling and successful or truncated generations do not trigger size correction.

Use the focused configuration, MCP/PostgreSQL and browser commands above against the current revision. Mocked provider responses validate prompt composition, scopes, publication and schema handling; they do not establish production-model quality. See [verification](../development/verification.md).

For Agent Studio specialists, **Model & limits → Agent execution** controls the total model calls, maximum corrections, specialist handoffs and whole-task timeout. Corrections and handoffs share the total budget. Prompts, skills, proposal guidance and narrative guardrails are managed in the feature instructions; native artifact fields, source permissions and approval remain enforced by the host. Create-agent definitions additionally declare an analysis or native authoring output contract and may impose lower execution limits. A completed request with missing required outcomes is shown as needing input rather than ready for approval.
