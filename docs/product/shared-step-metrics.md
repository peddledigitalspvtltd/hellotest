# Shared Step metrics

The Shared Step Groups page uses `/shared-step-groups/metrics?app_type_id=...` for exact server aggregates. It requires Shared Step and Test Case view permissions. Without both Run and Result view, execution counts and evidence are omitted; repository reuse remains visible.

- **Cases Reusing Shared Steps** counts distinct current test cases referencing a group in the same application. One case using multiple groups counts once in the page total.
- **Reusability Index** is `shared step execution instances / current repository test-step rows × 100`. Its execution window is the last 90 days, shown on the card. These are different units: repeated runs can produce a ratio greater than 100%. An empty repository has no ratio.
- **Shared Steps Executed** counts recorded passed or failed step outcomes, using the latest result attempt for each run/case/data row. It joins frozen step snapshots, so unlinking or editing a case cannot rewrite historical group membership. Native step-run outcomes take precedence over duplicate result-log evidence for the same frozen step. Blocked, skipped, pending, missing, malformed logs, and case-level failures do not prove shared-step execution.
- **Shared Failure Clusters** counts groups with failed shared-step evidence in at least two distinct cases in the window. Evidence links open the recorded run and case. A cluster supports investigation; it does not establish root cause. Cards display a bounded selection of evidence while counts cover the whole window.
- **Mean Time To Isolation** requires recorded failure and isolation timestamp pairs. There is currently no source for verified pairs, so it is unavailable. Case resolution, result edits and AI output are not substituted for isolation timestamps.

The group tiles show current definition completeness, observed shared-step pass rate, exact distinct case reuse, and shared-step execution/failure evidence. The run history strip shows the latest ten observed group/run outcomes; its preview limit does not truncate run or step counts. SQL aggregates avoid returning full execution logs to the browser. Scoped indexes support repository and frozen-snapshot usage lookups. Legacy plain-text logs safely provide no structured step evidence.

Native `test_case_runs.data_set_iteration_index` and `data_set_iteration_key` are nullable identity fields for integrations that write native `step_runs`. Current application callbacks persist iteration identity on `execution_results`; they do not write native step-run rows. No historical native row is backfilled or assumed to be row zero. Explicit indexes match indexes; keys match when either source lacks an index. Unidentified native outcomes only deduplicate legacy/default manual outcomes. When native outcomes have no identity and overlap identified manual outcomes without a matching default, affected execution/pass/fail totals and the overall Reusability Index are unavailable with a missing-identity explanation. Exact repository reuse and unaffected groups remain available.
