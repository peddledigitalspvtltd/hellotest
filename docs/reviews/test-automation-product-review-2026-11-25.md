# Test Automation product review

25 November 2026

## Product judgment

Test Automation has a usable end-to-end model. A case owns its behavior and implementation, the Object Repository and Shared Step Groups hold reusable assets, a suite defines which cases run together, and a Run records what happened with a particular environment and data. The deepest gaps were at the handoffs between those jobs. A user could lose the source behavior when creating an API build, lose track of a saved Run after a failed start, or see different results for the same case in the catalog and table.

The workspace now gives the user a short path to the next action. Plan shows the behavior, Instructions and Source expose the implementation, Test Data and Test Params own input changes, Build holds active work, and Runs holds evidence. Advanced settings, diagnostics, and reuse details appear where the user can act on them.

## Verification boundaries

- The integrated Automation and related workflow checks passed 2,167 tests with nine opt-in checks skipped. Chromium scenarios covered catalog commands, filter retention, saved Run recovery, recorder review, repository interaction, source editing, API authoring, and Test Data.
- Disposable PostgreSQL verified catalog evidence and pagination, repository dependency invalidation, transactional shared-group edits, and durable suite dispatch. The catalog checks included a finalized failure older than the ten-result trend sample and a run with multiple data iterations.
- The automation plan can be ready while execution remains unverified. A recorded action, generated script, and passing Run represent different evidence.
- Web recording supports the recorder’s portable interactions on a single page. Popup, iframe, and drag flows have separate authoring support through the Build Agent or direct source. Native mobile recording and execution use Appium and require a configured device.
- Full runs verify API and mixed flows, including response captures that later steps consume. The Web build can perform its own isolated verification when configured.
- Saved platform filters use the explicit platform saved on the case. A legacy case without that setting remains visible under Any platform.
- The review used local application fixtures, controlled Test Engine inputs, and disposable data. Connected project models, hosted browsers, and physical devices require environment-specific verification.
