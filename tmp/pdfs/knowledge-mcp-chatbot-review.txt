Verdict
The control side of this system is production-grade; the retrieval and reasoning side is not
yet. Authorization, provenance, budgets and the approved-plan write path are stronger
than most systems of this kind. Answer quality is held back by a lexical search defect, a
thin graph, untuned ranking and a chatbot that uses one tool in a fixed pipeline.
Seven changes matter most, in this order:
1. Fix the lexical search query so it matches on an index and tolerates sentence-length
questions.
2. Build an end-to-end retrieval evaluation set, then replace the hand-set score weights
with rank fusion plus a reranker.

Knowledge graph
The graph model is sound, but it holds too little to change answers. Nodes are knowledge
sources, one node per source, in nine kinds. Edges carry one of eight relation types, a
provenance level and a validity interval, and every active edge needs a chunk-span
witness pinned to a document version hash.
Keep these as they are: composite keys that stop an edge borrowing another project's
proof, the database constraint that an LLM candidate can never be active, the access
recheck after each walk, and the limitation notes returned with every result.

Context graph
The context graph is a per-user provenance ledger, and it stops one step short of being
useful for learning. Each delivered context packet becomes one trace holding up to 30
evidence references with version and chunk hashes. Up to seven event types attach to it,
and exploring a trace rechecks current access and freshness.
It stores no prompts, source bodies or model reasoning. The write is best-effort with a 1.5-
second limit, so it never fails the read it describes. Both choices are right.

Deriving the knowledge repo
The ingestion pipeline is correct but learns about change too slowly. A source becomes an
immutable document version, then chunks of 1,600 characters with 220 overlap, then
provider embeddings with a local hashed fallback. Graph and Qdrant projections follow
from PostgreSQL, which stays canonical.
Stories, test cases, runs and defects are turned into labelled text by four serializers. Keep
the immutable versions, the snapshot fingerprint that includes linked children,
embedding reuse by input hash, lease-based job claims, and the rule that run summaries
and result logs sit behind different permissions.

MCP tools
The MCP layer is the strongest part of the design, with one structural flaw: the chatbot
does not really use it as a tool contract. The server is a stateless POST endpoint with
about 70 tools. Every call rechecks the account, project membership, feature flags and
permission, validates output against a published schema, and writes one audit row.
The write path deserves to stay exactly as built. A plan is prepared with a digest, catalog
revision and captured target version. A person approves it. It executes once under a row
lock with an idempotency key, then a read-back verifies the effect, and an uncertain
outcome is recorded as unknown for reconciliation.

Chatbot: from intent to answer
The chatbot is safe and repeatable, but it is a fixed pipeline rather than an assistant that
uses tools. A turn runs these steps, capped at 120 seconds and delivered as one result:
1. Sanitize the question and make the turn idempotent by client turn ID and fingerprint.
2. Refuse out-of-domain and sensitive-disclosure requests with pattern checks, before
any retrieval.
3. Optionally ask the model for a plan: up to three queries, source kinds, information
needs and a strategy. Each query must share a word with the question.
4. Make one context_build  call through the MCP gateway.
5. Make one synthesis call against a JSON output schema, with one repair attempt.
6. Re-authorize every cited source and drop claims whose evidence is no longer visible.
7. Save the answer, then record the outcome on the context trace.
